# 评测（Evaluation）

> **English summary.** What was measured, how, and what the numbers do and do not show. Highlights: the citation check never gave a ✓ to a wrong citation in 81 labelled pairs (with an honest note on how little 12 wrong pairs can prove); five rounds of the question-decomposition harness plateaued at 61–70 / 90, and a blind A/B against a single call tied overall at 5× the time and 63× the input tokens, which led to replacing it; a full real-model run takes about 40 minutes. Sample sizes are small and judged by one person; each section says so.

每一节都写清楚四件事：测的是什么、怎么测的、结果、这些数字**不能**说明什么。样本都不大，判分大多是一个人，所以第四件事和结果一样重要。

<a id="citation-checks"></a>
## 1. 引用三道关（挂 ✓ 之前的核对）

- **测什么**：一个脚注拿到 ✓，就意味着"原文撑得住这句话"。最不能接受的错是把挂错的引用标成 ✓。
- **数据**：从真实报告里取 81 对"正文句 + 原文句"，由一位标注者逐条判：撑得住 36、部分 33、挂错 12。按报告分组送检，和真实运行一样。
- **做法**：代码核对数字和专有名词 → DeepSeek 判 → Kimi 独立判，三道都过才挂 ✓。脚本：`scripts/eval-citation-verify.ts`，数据：`tests/fixtures/d48/citation-pairs.json`。
- **结果**：

  | 跑法 | 撑得住 36 → ✓ | 部分 33 → ✓ | 挂错 12 → ✓ | 一份报告用时 |
  |---|---|---|---|---|
  | 严格提示词，第 1 次 | 9（25%） | 2（6%） | **0** | 109–209 秒 |
  | 严格提示词，第 2 次 | 11（31%） | 4（12%） | **0** | 109–200 秒 |
  | Kimi 关思考 | 10 | 3（9%） | **0** | 5–8 秒 |

- **选择**：要的是"挂错 0"，接受"撑得住的只有约三成拿到 ✓"。代价是页面上 ✓ 少：一份试水报告 20–30 个脚注里约 5–8 个有 ✓，其余显示灰色。
- **不能说明什么**：挂错样本只有 12 个。0/12 的意思是：按"三分之一法则"，**真实的错挂率 95% 置信上限约为 25%**，远不能说"永远不会挂错"。要把上限压到 5% 以下，需要约 60 个挂错样本也全部拦住。另外标注只有一个人，"撑得住"的标准本身就有分歧（见[模型行为观察 §1](model-behavior.md#stricter-than-people)）。

<a id="decomposition-harness"></a>
## 2. 研究计划的拆题 harness：五轮没有变好，于是换掉

- **测什么**：给一个战略问题，拆出的计划好不好、稳不稳。
- **做法**：5 道固定题（题目清楚、含糊、跨领域、方针冲突且前提可疑、很小的题），每题跑 3 次，共 15 份。6 项各 1 分（够不够、不重叠、能证伪、扎根于资料、和高层方向对齐、说人话），满分 90。另记"稳定性"：3 次的维度和一级问题对不对得上。
- **结果**：

  | | 第 3 轮（基线） | 第 4 轮 | 第 5 轮 | 第 6 轮 | 第 7 轮 |
  |---|---|---|---|---|---|
  | 总分（满分 90） | 61 | **70** | 64 | 65 | 63 |
  | 稳定的题数（共 5） | 3 | 1 | 0 | 4 | 4 |
  | 用户能看到的缺陷（15 次里） | 末句截断 4、代号 1 | 问用户拆法 2 | 内部编号 5、占位符 3 | 内部编号 3、占位符 1 | 占位符 3、重试话术 2、编号 1 |

- **读法**：加结构让"稳定"从 0/5 升到 4/5，但总分在 61–70 之间来回，**没有一轮超过第 4 轮**。每题只有 3 次，±5 分的变化分不出是改进还是波动，所以不能把任何一轮的提升当成真的变好。
- **决定**：拆掉这套结构，换成"契约 → 整体判断 → 独立评估 → 修订一次 → 编成树"的薄循环（[D-61](design-decisions.md#d-61-a-thinner-harness)），同时把"稳定"重新定义为"每次抓住同样的关键不确定性"。
- **随后做了 A/B 盲评，看看结构到底值多少**：
  - **A**：把问题和资料包一次交给 `deepseek-flash`，直接写；**B**：冻结的第 7 轮流程（每次约 20 多次模型调用）。同一个模型、同一份资料包。
  - 8 道题（1–5 题和资料包的领域相关，6–8 题无关）× 每组 3 次 = 48 份；随机编号、去掉版本标记后交给评审人盲评，按严格口径（每个假设都要写证伪条件）打分，另加"抓住关键不确定性"和"有没有决定不了任何事的研究"两项。

  | | A 直接一次 | B 冻结的 harness |
  |---|---|---|
  | 1–5 题（本领域）均分 | 5.00 | **5.87** |
  | 6–8 题（无关领域）均分 | **4.89** | 4.00 |
  | 全部 24 份均分 / 中位数 | 4.96 / 5 | 5.17 / 6 |
  | 用时（中位数） | **53 秒** | 265 秒 |
  | 输入 / 输出 token（中位数） | **2,286 / 6,835** | 144,208 / 44,170 |
  | 没产出 | 0 / 24 | 1 / 24 |
  | 挂了不该挂的依据 | 1 / 24 | 9 / 23 |

  - **读法**：总分差 0.2，在噪声以内（评审人估计"扎根"一项本身就有 ±0.5 的误差；A 有 21 份恰好 5 分，区分度很低）。B 在本领域的题上确实更好，但在无关的题上更差：两份答非所问的计划，原因是流程强制把资料包里的每条高层指示都写进前提，哪怕和问题无关。为了这点收益，B 用了 5 倍的时间和 63 倍的输入 token。
  - **结论**：结构不是没用，但它的收益很窄，代价很大，而且会把不相关的上下文硬塞进去。这支持了 D-61 的方向：先写整体判断，再用独立评估挑毛病，资料只按需引用。
  - **不能说明什么**：每题只有 3 次，只有一位评审人；新的 D-61 流程还没有加进同一套盲评做第三组。

## 3. 真实模型完整走查

- **做法**：用真实模型（判断 Kimi，执行 DeepSeek，联网走 DeepSeek Search / Fetch），由脚本在浏览器里按完整流程自动走一遍：新建项目 → 研究计划 → 按意见修改 → 调查计划 → 资料选择 → 调查执行 → 报告 → 访谈建议 → 追加分析 → 决定确认 → 下一条工作线复用。脚本：`scripts/real-walkthrough.ts`；存档快照：`demo-vault/.snapshots/m1-qira-done`。
- **结果**：全程约 40 分钟；调查执行 19 分钟，联网搜索 13 次、读网页 31 次；报告交付，引用全部过了自检。
- **和直接问模型的差别**：

  | | 直接问一次 | 工作台 |
  |---|---|---|
  | 回答 | 几类用户画像平均着墨，不排序，不说先做哪一类 | 一句话回答要做的决定：现有证据不足以支撑主押，写明缺什么、怎么验证 |
  | 数字 | 有留存率之类的数字，没有样本、口径和出处 | 每个事实带脚注，点开是原文和三道核验；没有证据的数字不写 |
  | 事实和推测 | 语气一样肯定 | 逐条标"事实 / 推断" |
  | 复用 | 留在个人对话里 | 下一条工作线开工时，AI 把这条已确认的决定列为第一份要读的资料 |
  | 成本 | 一次提问 | 约 40 分钟，多次模型调用 |

  结论方向不一定不同，差别在于**结论能不能被检查、讨论和拿来做决定**。简单问题直接问模型就够了。

## 4. 成本和延迟

待补：每次运行的各段用时、模型调用次数、输入和输出 token、缓存命中的 token 和花费。

**怎么复现**（需要 `DEEPSEEK_API_KEY` 和 `MOONSHOT_API_KEY`）：

```bash
pnpm exec tsx scripts/demo-snapshot.ts make m1 && cp -R .scratch/m1 .scratch/m1-real
USAGE_LOG=.scratch/usage.jsonl VAULT_DIR=.scratch/m1-real NEXT_DIST_DIR=real pnpm exec next dev -p 3005 -H 127.0.0.1
pnpm exec tsx scripts/real-walkthrough.ts --base http://127.0.0.1:3005 --vault .scratch/m1-real --out .scratch/real-run
pnpm exec tsx scripts/usage-report.ts .scratch/usage.jsonl --prices prices.json
```

- `USAGE_LOG` 打开以后，每次模型调用都会记一行：token、缓存命中、推理 token、耗时（`lib/models/usage-log.ts`）。
- `usage-report.ts` 把空闲超过 10 分钟的地方当作两次运行的分界，按模型汇总；价格从 `prices.json` 读（每百万 token，按各家当时的官方价格填），不内置任何价格。
- 走查脚本每一步都会在 `.scratch/real-run/run.log` 里记下累计用时；联网搜索和读网页的次数记在报告的 `research_run` 里。

## 5. 工程测试

- 约 3,000 条单元测试（vitest），70 条左右端到端测试（Playwright，模型和联网都用脚本替身，结果可复现）。
- 用户能看到的文字里不能出现内部名称（文件名、工具名、块编号、vault 路径）：有专门的检测函数和单元测试（`lib/testing/internal-names.ts`），研究计划的输出在交给用户之前也会过一遍清洗（`lib/workplan/compose/scrub.ts`）。
