# 设计决策（Design decisions）

> **English summary.** This project went through 64 recorded decisions in about a week. Below are the ones that shaped the product, each as *the problem at the time → what was chosen → why → what happened after*. The recurring lesson: when a model keeps making the same class of mistake, move that rule out of the prompt and into code, a gate, or a person's checkpoint, then measure whether it actually helped.

开发过程中一共记了 64 条决定（D-1 到 D-64），其中有不少后来被推翻。下面挑出塑造了产品的十条，每条都按"当时的问题 → 选了什么 → 为什么 → 后来怎么样"来写。贯穿始终的一条经验是：**模型反复犯同一类错误时，就把那条规则从提示词里拿出来，交给代码、关卡或人，再量一下到底有没有用。**

---

<a id="d-1-a-markdown-vault-instead-of-a-database"></a>
## D-1 A markdown vault instead of a database

- **问题**：团队的积累需要"数据层 + 语义层"：原始资料、从资料里抽出的论断、方法、项目状态、决定。做一个真正的数据库不现实。
- **选择**：数据层和语义层都用一个 Obsidian 式的 vault：markdown 加 frontmatter，用双链连接，论断用块编号（`^c1`）。
- **为什么**：语义层存的本质上是结构化文本，markdown 加 frontmatter 加双链装得下；而且任何一句话都能点开看出处。数据库真正不可替代的是并发写入、权限和大规模检索，演示阶段都用不到。
- **代价（写明了）**：单机、没有权限模型、检索靠全文和索引。上线时这一层要换。

<a id="d-8-two-layers-research-plan-and-investigation"></a>
## D-8 Two layers: research plan and investigation

- **问题**：最初把"这项工作打算怎么做"和"去查资料"混在一个对话里。
- **选择**：拆成两层。**研究计划**面向负责人，回答"打算怎么做"，可以征求意见；**调查**是执行工具：先问清楚，出一份按假设组织的调查计划，人改过、批准以后才能执行。
- **为什么**：两层服务的人和节奏不同。把"计划批准"做成执行的前提，就能由系统保证"没批准不上网"，而不是靠模型自觉。

<a id="d-29-a-citation-to-a-document-that-does-not-exist"></a>
## D-29 A citation to a document that does not exist

- **问题**：一份报告引用了一份"监管指引"，原句和出处对得上，但这份指引根本不存在：来源是文库平台上一份用户上传的文档。人工去官网核实后才确认。
- **认识到的**："引用对得上原文"不等于"原文是真的"。之前只验证了前者。
- **选择**：
  - 资料加一个可靠性字段，证伪过的来源不再进入检索；
  - 用户上传类平台的资料一律定为 C 级、标"转述"；
  - **论断要判"成立"，需要至少 2 条互相独立的来源，其中至少 1 条是 A 或 B 级**；过不了门槛的标"待验证"，转成要问专家的问题。
- **后来**：这条证据门槛成了整个判断引擎的基础。

<a id="d-51-freeze-the-judgment-let-code-assemble-the-rest"></a>
## D-51 Freeze the judgment, let code assemble the rest

- **问题**：报告质量"修一处、冒一处"。一次自动修复引用的步骤，把原本判"成立"的条件降成了"还缺证据"，分号被吞，推荐表和正文前后矛盾。
- **根因（第一性原理）**：每一层都让模型把上一层的自由文本重写一遍：判断 → 回答 → Summary → 推荐 → 修复。每多重写一次，就多丢一次信息、多出一次错。正确性全靠模型自觉，违背了"规则由系统执行，不靠提示词"。
- **选择**：
  - 判断冻结成文件，后续只改写法的重写一律读这份判断，不再重判；
  - 回答按条件分段，语气由代码按条件状态决定，Summary 由代码拼装；
  - 写作的模型只输出引用编号，脚注全部由代码渲染；
  - 专有名词和数字由代码核对，**只标 ⚠，不改正文**。
- **后来**：这一类"改坏"的问题没有再出现。人工修正功能保留，只作兜底。

<a id="d-52-stop-patching-define-the-finish-line"></a>
## D-52 Stop patching: define the finish line first

- **问题**：3 天里定了 51 条决定，至少推翻了 9 次；"最多再修一轮"的停止规则破了两次；评分表一轮都没正式打过。每一轮都是：重跑 → 发现新一类缺陷 → 加一条提示词规则 → 再重跑。
- **选择**：
  - 先定目的（证明论点，而不是做完美产品）；
  - 再定终点线：评分表连续两轮全过；只有 4 条可以一票否决（读不通或自相矛盾、挂错且没标 ⚠ 的脚注、没有正面回答核心问题、文档说了但做不到）；其他发现一律记进路线图，不触发新工作；
  - 评审先交给一个只读评分表和被审对象的评审子 Agent：最多列 3 条"必须改"，每条指到原句，不提修法；再交给人。
- **为什么**：没有终点线时，每个新发现都会变成新工作。把"什么算失败"写死，才停得下来。

<a id="d-56-three-checks-before-a-footnote-gets-a-tick"></a>
## D-56 Three checks before a footnote gets a ✓

- **问题**：引用"对得上原文"已经由结构保证了，但"原文撑不撑得住这句话"还要靠人逐条点开看。
- **选择**：每个脚注过三道关，三道都过才挂 ✓，其余显示灰色"相关资料（未核实能不能撑住这句话）"：
  1. 代码核对：句子里的数字和专有名词在引文里出现；
  2. DeepSeek 判一次；
  3. Kimi 独立判一次（关掉思考），和第 2 道同时跑。
- **验收口径**：挂错的 ✓ 必须是 0；能拿到 ✓ 的比例是次要的。
- **结果**：81 对人工标注的样本里，挂错的 0 个拿到 ✓；但"人认为撑得住"的只有约三成拿到 ✓。我选了严格的这一头，演示时只点 ✓。详见[评测](evaluation.md#citation-checks)。

<a id="d-60-separate-judgment-from-execution"></a>
## D-60 Separate judgment from execution

- **选择**：判断类的步骤（问清楚、起草调查计划、"内部资料够不够"的建议、结论、推荐）交给 Kimi；执行类的步骤（检索、抓取、抽证据、自检修复，按已经定好的判断写正文）交给 DeepSeek。在配置里按角色路由，换模型只改一行。
- **实测**：同一道题，Kimi 标准版 240 秒没有返回，高速版 31 秒答完。现场等不起，所以产品用高速版。
- **后来**：在研究计划这一段，两个模型接力反而丢信息（一个定拆法、另一个写树，后者看不到前者为什么这样拆），D-61 把这一段改回单模型。调查那一段保留分工。

<a id="d-61-a-thinner-harness"></a>
## D-61 A thinner harness

- **问题**：研究计划的拆题 harness 连续五轮评测（5 题 × 3 次，满分 90）得分 61、70、64、65、63，**没有一轮超过第二轮**。加上的结构（代码定拆法、7 种固定拆法、结构化 JSON、一次写完整棵树）让结果**更稳了，但没有更好**。
- **诊断**：拆得太早；多模型分工丢信息；评审只审形式，不审价值。
- **选择**：换成一个薄循环，每一步由代码守边界：
  0. 决策契约（要回答什么、支撑什么决策、范围、成功标准、已知事实、证据要多强才能拍板）；
  1. 不限格式的整体判断草案；
  2. 战略评估器：**全新上下文**，只看契约和草案，逐条回答 6 个问题，有问题的必须抄原话、给反例和改法，笼统的反馈由代码打回；
  3. 修订，最多 1 轮；
  4. 编成问题树和可证伪的假设。
  - 另有 token 和时间预算：软限制跳过评估并如实标注，硬限制拒绝新的调用。
- **同时改了"稳定"的定义**：从"每次拆法一样"改成"每次抓住同样的关键不确定性、假设能被证伪"。
- **为什么**：这是一次承认自己的设计没用的决定。数据说结构没带来质量，就把它拆掉。

<a id="d-64-gather-until-two-empty-rounds"></a>
## D-64 Gather until two rounds bring nothing new

- **问题**：早期的调查查完内部资料会停下来问人"够不够"，用户体验断成两截，人也很难判断。
- **选择**：内部资料不够时自动上网补查；**连续两轮没有新证据就停**；预算用完只交付已经验证过的部分。入库之前先过滤明显不是内容的页面（隐私政策、登录页、社交平台单条帖子），没有可核对原文的页面不入库。
- **为什么**：停止条件应该由证据的边际收益决定，而不是由人在中途拍脑袋。

<a id="principle-ai-proposes-people-decide"></a>
## 贯穿的原则：AI 只提议，状态只有人能改

- 模型永远拿不到"改状态"的工具：计划批准、报告确认、决定确认都是人点的按钮，写成审批事件。
- 模型在每个阶段只拿到这个阶段的工具（`lib/harness/phases.ts`），阶段由服务器根据 vault 的状态推出，模型改不了。
- 已确认的决定会被同一个项目里下一次调查检索到，并标明"已确认的决定"；还没确认的决定检索不到。
