# workplan 共创

> 用途：Junior 领题以后、动手查资料之前，AI 和 Junior 一起把"这项工作我打算怎么做"想清楚，写成 workplan 交给 Senior 在 G1 看。
> workplan 不是调查结果，是**开工前的判断**：问题对不对、拆得对不对、先做哪个、做出来大概长什么样。Senior 在这一步花 10 分钟，能省掉后面几天的返工。

## 什么时候用

- Junior 刚领到一个 Workspace，stage 是"拆题中"。
- workplan 被 G1 打回，要出新版本（先走 [[comment意图解读]]，再回到这里改）。
- 调查结果推翻了某个假设、或者范围变了，要更新 workplan 交给 Senior 看。

不要用在：已经有批准过的 workplan、只是要执行其中一项 next action 的时候（那是 [[假设驱动调查]]）。

## 怎么问（grill 的规则）

1. **一次只问一个问题。** 每个问题给 2–4 个选项，并说出你推荐哪个、为什么。Junior 可以选，也可以自己写。选项要列全，不能漏掉一条走得通的路（"押哪一层"这类问题怎么列全，见第 1 步）。
2. **能查到的不要问。** 先读 `项目.md`、`会议/` 里的高层指示、`决策/` 里已确认的决定、依赖的 Workspace 的结论。问之前说"我在 X 里看到 Y，所以我推荐……"。
3. **已经定了的事不重新讨论。** 已确认的决定是前提，写进 workplan 的"前提"一节。要推翻它，要单独提出来，交给 Senior。
4. **答得含糊也不要替 Junior 补全。** "都挺重要"、"看情况"这类回答，只有当含糊的正好是最影响拆题的那一件事时，才花一问追问（请他排出第一位、说清看什么情况）；否则原样记进 workplan v1 的"待确认"。
5. **从第一性原理出发**：先问"这个问题为什么存在、谁要拿答案做什么"，再谈怎么拆。不要从"业界一般这么分"开始。
6. **最多 3 问，到了就停。** 每问只问最影响拆题的那一件事：会改变问题怎么拆的先问（要支撑的决策、最可能推翻答案的子问题），只影响细节的（方法、停手标准这类）不问，先给出推荐值写进 v1。没问清的写进 workplan v1 的"待确认"，由 Senior 在 G1 看，不再继续问；追问也算在这 3 问里。

## 步骤

### 1 定核心问题：它要支撑什么决策

先把题目改写成一个**决策导向的核心问题**。要问清楚：

- 这个答案给谁用？他拿到以后要做什么决定？（例：VP 要决定明年 AI PC 的商用资源是投在"管理能力"还是"端侧算力"上）
- 答案是"是"和"否"，这个决定会有什么不同？如果两种答案下决定都一样，这个问题不值得做。
- **决策有哪些选项，列全了吗？** 选项要互不重叠，合起来覆盖所有走得通的路。"押哪一层"这类问题，选项有两维：押在哪里（例：管理 / 安全栈、端侧算力、agent 本身），以及怎么拿到——**自研、合作还是收购**。只列第一维，等于默认了自研，后面就不会去比合作和收购在成本、速度、风险上的差别。
- 时间和范围：这周要交什么、切片边界在哪（哪些客户、哪个时间窗、哪个地区）。
- 高层有没有已经给过的方向或偏好？（查 `会议/`）

核心问题只问一件事。一句话里有两个问号，通常说明它其实是两个子问题，放到第 3 步去拆。

好的核心问题：**"企业 IT 会不会在 2027 年为员工的端侧个人 AI 付费？如果会，决定付费的首要条件是什么？"**
差的："研究一下企业对 AI PC 的看法。"（没有决策、没有边界、做到哪算完不知道）

### 2 先写 Day-1 answer：现在就敢说的一句话答案

在还没查之前，用一句有判断的话回答核心问题。这是**假设，不是结论**，作用是：

- 逼自己选一个方向，后面拆问题、写假设才有东西可对照（没有答案，只能从话题出发，容易退化成话题清单）；
- 让 Senior 一眼看出拆解有没有走偏。

写法见 [[storyline]]。key message 必须是一句有判断的话，不是"本章介绍……"。如果问题是"押哪一层"，答案要同时说押在哪里、怎么拿到（自研 / 合作 / 收购）。
**锚定风险**：第一个答案容易变成唯一的答案。所以第 5 步必须为它专门写反证，第一版答案被证据推翻是正常的，改它不算返工。

好的 Day-1 answer："联想明年在商用 AI PC 上应该把差异化押在 IT 可管的个人 AI 层，而不是继续堆算力。"
差的："AI PC 市场很大，联想应该积极布局。"（没有方向，无法被推翻）

### 3 拆问题：核心问题 → 子问题

问："要回答核心问题，必须先回答哪 3–4 个小问题？"把核心问题拆成能回答的子问题。

- 每个子问题是一个**问句**，不是一个话题，也不是一句判断。"预算来源"是话题；"员工个人 AI 的预算会从软件订阅预算里出"是判断，放到第 4 步当假设；"这笔钱从哪个预算出？"才是子问题。
- 子问题按 MECE 拆：
  - **不重叠**：同一条证据能同时回答两个子问题，就是重叠了。把重叠的那件事指定给其中一个子问题，另一个只引用它的结论。
  - **不遗漏**：几个子问题都答了，核心问题就能回答吗？还缺什么？少了"凭什么是我们"那一问，一定不充分。
- 检查充分和必要，并**写下理由**：
  - **充分**：这几个子问题都答了，核心问题就答了。写一句为什么。
  - **必要**：拿掉任何一个，核心问题就答不了。对每个子问题写一句"少了它，就不知道……"。写不出来，就删掉它。
- 一个子问题太大、一次答不了，可以再往下拆一层（Q2 → Q2-1、Q2-2），同样按 MECE 拆。**最多拆两层。** 拆到第三层，通常是把检索要查的东西当成了子问题。
- 拆法从问题本身来，不从话题来。常用的拆法：按先后的步骤（例：买方谁说了算 → 按什么标准放行 → 钱从哪出），按决策的选项，按"必须同时成立的几件事"。
- **必须有一个子问题回答"凭什么是我们"。** 拿这一层**最强的**对手来比，不拿行业平均：对手已经有的东西，联想再做一遍凭什么赢，买方为什么要换？本项目押管理 / 安全栈这一层时，最强的对手是微软的 Intune 和 Agent 365。这个子问题的答案是否定的，核心问题的答案再好也只说明"这一层值得做"，不说明"该联想来做"。这一问交给别的 Workspace 回答时，要写明交给了谁。
- 排优先级：**最可能推翻答案的、或者最不确定的，先做。**

### 4 写假设：每个最底层的子问题一条

每个最底层的子问题（没有再往下拆的那些），**有且只有一个假设**，就是现在对这个问题最好的回答。假设要**可证伪**：说得出什么证据会让它不成立。

- 有方向：说清楚是"会"还是"不会"、"大于"还是"小于"。
- 有条件：在哪类客户、哪个时间窗里成立。
- 有门槛：能用数字的用数字（"超过一半的 CIO 把……排在前三"），没有数字就写清楚判断标准。

好的假设："大企业 IT 采购员工端侧 AI 时，可管理性（能集中部署、管控数据、审计）是排在算力之前的首要条件。"
差的假设："IT 管理很重要。"（无法被推翻，也就没有信息量）

一个子问题想写两个假设，说明这个子问题还能再拆。

每个假设单独写成一条 `hypothesis` 笔记，`workspace` 指向本 Workspace。

### 5 写每个假设的验证计划（含反证）

对每个假设写清楚：

| 要写的 | 说明 |
|---|---|
| 必须成立的条件 | 如果这个假设是对的，世界上必须有哪几件事是真的？一般 2–3 条 |
| 要什么证据 | 每个条件，什么样的事实能证明它？什么样的事实能推翻它？ |
| 去哪里查 | 一手信源优先：厂商财报和官方发布、监管文件、官方统计；其次是研究机构和主流财经媒体 |
| 用什么方法 | desk research（知识库 → 网络）、专家访谈、数据分析，选一个主方法 |
| **怎么找反证** | **必填**：如果它是错的，会在哪里留下痕迹？对 Day-1 answer 本身也要写一条 |
| 做到什么程度停 | 什么情况下就能下判断，什么情况下标"证据不足"转专家 |

只写"desk research"不算写了方法。

### 6 next action

写到"明天早上打开电脑就知道做什么"的程度：做哪件事、用什么工具（例：对 H1 跑一次 Deep Research）、要找谁（专家、BG 接口人）、什么时候给 Senior 看。

## workplan 的结构（写 `workplan v<N>` 时照这个顺序）

1. 核心问题，它支撑的决策，以及决策的全部选项（押在哪里 × 自研 / 合作 / 收购）
2. 前提：用到的高层指示、已确认的决定（都要链接）
3. Day-1 answer（一句话）
4. 问题树：核心问题 → 子问题（最多两层）→ 每个最底层的子问题一条假设（链接到 hypothesis 笔记），按优先级排；其中一个子问题回答"凭什么是我们"，写明拿哪个对手比
5. MECE 和充分必要的自检：怎么拆的、为什么不重叠、为什么不遗漏、少了每个子问题会答不了什么
6. 每个假设的验证计划（上面那张表，含反证）
7. 金字塔骨架
8. 风险和待确认：哪里最可能被推翻；没问清、先按推荐值写下的事项，要 Senior 在 G1 帮忙判断什么
9. next action

## 好的 workplan 和差的 workplan

| | 好的 | 差的 |
|---|---|---|
| 问题 | 写出了谁要做什么决定 | 只有研究主题 |
| 选项 | 列全了；"押哪一层"同时写了自研 / 合作 / 收购 | 只列了做哪一层，默认自己做 |
| 竞争 | 有一个子问题拿最强的对手比"凭什么是我们" | 只证明"这一层有价值"，没问联想凭什么赢 |
| 子问题 | 3–4 个问句，MECE，写了为什么充分、为什么每个都少不了 | 一串话题清单（"市场规模、竞争格局、用户需求……"），或者把判断句当子问题 |
| 假设 | 每个最底层的子问题一条，可证伪，有条件和门槛 | "很重要""有影响"；一个子问题挂了好几个假设 |
| 验证计划 | 每个假设写了必须成立的条件、证据、信源、反证 | 统一写"desk research" |
| 答案 | 查之前就有一句 Day-1 answer，并写了反证 | 结论留到最后"看查出来什么"，或者答案一旦写下就不再质疑 |
| 前提 | 链接了高层指示和已定的决定 | 看不出知不知道高层说过什么 |

## 常见错误

- **跳过问题定义，直接开始查。** 最贵的错误：查了三天才发现问题不对。
- **Day-1 answer 写成了结论，不再找反证。** 它只是第一个假设。
- **把话题当子问题。** 话题清单永远 MECE，但不回答任何问题。
- **把判断句当子问题。** 判断是假设，要挂在子问题下面；子问题必须是问句。
- **假设写得太安全**，什么证据都推不翻它。
- **子问题太多，或者拆得太深。** 顶层超过 5 个、或者拆到第三层，通常是没想清楚哪个最关键。
- **只写"MECE"，不写理由。** 自检要写出为什么不重叠、为什么不遗漏、少了每一个会答不了什么。
- **只证明了这件事值得做，没证明该我们做。** 没有"凭什么是我们"的子问题，结论换成任何一家厂商都成立。
- **忽略高层指示或已确认的决定**，又从头论证一遍。
- **AI 替 Junior 做了判断。** AI 推荐、给理由；选择由 Junior 做，并且记下他为什么这么选。
